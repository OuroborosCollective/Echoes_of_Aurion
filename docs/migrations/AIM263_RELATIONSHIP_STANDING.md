# AIM-263: standing from actual quest receipts

This increment wires Aurion's native quest and authored faction quest completion transactions to the existing scoped mastery event store. It uses AX1 d356881's seven standing thresholds and the existing socialMasteryEvidence mapping: native quest assistance is friendship (4 scoped XP, +5 NPC standing), authored faction completion is diplomacy (5 scoped XP, +4 faction standing). The adaptation is versioned as aurion-standing-receipts.v1. Initial standing is zero; no prototype faction/leadership bonus is copied.

Two coupled events are written inside each owning reward transaction. Their IDs bind user, immutable completion receipt and scope with SHA-256. They cannot be submitted directly by a client. A failed event insertion rolls back the native quest state and base reward. Native completion now verifies an owned completed encounter with zero boss HP before awarding the base reward. Faction rewards take the player-profile lock before their faction-state lock to serialize profile rewards.

Readback is an authenticated owner-only query. It reconstructs expected events from the actual completed native encounter/quest or authored faction reward/decision. Hashes, source owner, scope, complete coupled pairs and authored reward digest are checked. Returned XP/levels use the existing exact uncapped mastery resolver. Reads above the bounded event budget fail with checkpoint-required rather than return partial totals.

The existing aurionScopedMasteryEvents.professionReceiptId column stores these source receipt identifiers as well; it has no crafting-only foreign key. No profession receipt is fabricated. Crafting readbacks continue to select their own scopes. A future schema rename can make the historical column name clearer without changing this source binding.

Contacts show Lyra/Orun relationships and factions with confirmed events, together with social mastery. Empty evidence is labelled explicitly. Runtime validation rejects foreign or inconsistent readbacks; stale/error states remain visible and refreshable. Negative relationship events and their gameplay callers remain open; the threshold function already validates all seven tiers. No permissions derive from displayed standing.

Completed historical quests receive no invented retroactive credit. Native loot/combat/weapon finalizers remain the existing idempotent recovery stages outside the base transaction; this does not claim a universal atomic quest outbox.

Validation: 8 targeted standing/HUD tests and TypeScript pass. New isolated MariaDB cases cover native grant/replay/owner isolation, relationship-insert rollback and actual authored faction reward with corrupt-event rejection. The authenticated browser test also checks visible +5 NPC standing and both exact stored event hashes after actual quest combat/turn-in. CI outcomes and deployment are recorded separately in Linear.

The first real faction-reward test exposed an existing missing replay lane: the reward transaction advanced lastResolutionIndex, but the state resolver knew only decision/oath indices, causing valid completion to roll back. Completion receipts now participate in the checked causal index and deterministic state hash. Rehydration validates the authored reward against the owned decision and stored digest. The equality check against the newest receipt is retained. Concurrent faction completion locks the profile before any replay read; the DB test requires exactly one grant and identical receipt IDs, then executes a later authored decision and checks persisted reward tampering.
